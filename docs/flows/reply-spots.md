# Reply spots (the core copilot)
> Goobi scans your X timeline, asks Claude to score each post for reply-worthiness, badges the good ones, drafts a reply in your voice on demand, and types it into X's reply box without ever posting.

**Surface:** Ambient on x.com / twitter.com (content script `src/content/x-copilot.ts`, injected only on those hosts). It paints inline badges on timeline posts, an always-on bottom-right "dock" listing ranked reply spots (`dockView === "replies"`, the default mode), and a closed-shadow-root draft panel. Settings (key, niche, voice, products) live in the extension popup/side panel.

## What it does for the user
As you scroll X, it quietly flags the handful of posts where a reply is actually worth your time, and tells you why and what angle to take (add value, ask, joke, promote, etc.). When you pick one, it writes a reply in your own voice, grounded in the thread, and drops it straight into X's reply box for you to review and post. It deliberately surfaces only ~1 in 8-10 posts and decays stale spots, so it points you at fresh, reachable, genuinely-fitting conversations rather than every post on screen.

## How the user uses it
1. Scroll the X timeline normally. Posts worth replying to get a brand-orange left border + a pill badge like `✦ 78% · Add value` (score = reply fit, tag = angle). Posts the scorer saw but passed on get a faint `+ Add` you can click to override and pull them in.
2. Open the dock (bottom-right) to see the ranked list of collected spots, sortable Best / Recent / Reach / Easy, filterable by author/text. Each card shows the author, avatar, age, engagement, fit verdict, and category.
3. Click a badge or a dock card to open the draft panel. It shows "Drafting in your voice…", then a textarea with the reply, angle chips (Connect / Add value / Ask / Joke / Support / Promote — a ★ marks your measured-best angle once ≥2 angles have ≥4 settled outcomes each, `learnFeatures`), a "Steer it" free-text input, Copy, and ↻ Regenerate.
4. Optionally switch angle (re-drafts), type a steer + Regenerate, or edit the textarea by hand.
5. Click "Insert into reply box." Goobi opens the post's reply composer, types the draft in, likes the post (once), and shows a toast (plus any pacing/duplicate nudge). You review and hit Post yourself — it never submits.
6. Optional extras: ⟳ Rescan re-evaluates the visible feed from scratch; "Find spots" searches X (RapidAPI) for fresh niche posts off-page; Pause goes quiet. The **minimized pill carries ⏸/▶ pause and ✦ Find-spots controls too** (stopPropagation — they act without expanding the dock; ✦ disables while paused/searching).

## How it works
**Trigger / scan.** A `MutationObserver` on `<body>` + a URL poll call `requestScan()` (rAF-coalesced). `scan()` (x-copilot.ts) walks every `article[data-testid="tweet"]`, extracts `{id, author}` via `statusInfo()`, skips ads (`isPromoted`), your own posts, in-flight and already-`seen` ids, re-badges cached ones, and pushes the rest onto a `queue` (text capped 400 chars). **At ease-off (≥30 replies/hr) the ambient scan PAUSES entirely** — no new queueing, no Haiku spend: surfacing more reply spots while the user should cool down contradicts the honest mirror. Manual actions still work: ⟳ Rescan opens a 2-minute override window (`manualScanUntil`) and Find spots doesn't route through `scan()`; the ease-off callout says "Goobi paused scanning (⟳ Rescan overrides)". On `/notifications` it diverts to `scanNotifications()` instead.

**Score (Claude, Haiku).** `scheduleFlush()` debounces 900ms, then `flush()` `splice`s up to `BATCH = 12`, increments `scoreCalls` (capped at `MAX_SCORE_CALLS = 40` per page-session), snapshots stats (`snapStats` → `postedAt`, likes, replies via the action-bar aria-label), and sends `SCORE_POSTS` to the service worker. `service-worker.ts` reads the stored niche + products and calls `scorePosts()` (claude-client.ts) → `claude-haiku-4-5`, `X_SCORE_SYSTEM`, `max_tokens 1024`. The model returns `{i, score 0-1, reason ≤6 words, category, products?}`; product NAMES are resolved SW-side from indices. Back in `flush()`, results land in `seen` (dedup cache) and, if `score >= THRESHOLD (0.6)`, in the `opps` map; below-threshold gets a `+ Add` button (manual opps are never pruned). Only posts text+author go to Claude — timing/reach are computed locally so a stale post can re-rank without a re-call.

**Rank (local, live).** The dock and badges show `effectiveScore(o)` (x-copilot.ts), NOT the raw model score: `score × freshnessFactor(postedAt) × reachFactor × buried`, plus a builder-peer lift (`builderTierFor`) and a niche-peer freshness floor. `freshnessFactor` decays hard (1.0 under 5min → 0.08 past a day) so timing dominates by design. `reachFactor` folds in the author's real follower count (Twttr) with a 5x-25x reach sweet-spot bump (`inReachSweetSpot`), a mega-account discount, and a `reciprocityFactor` from following/followers ratio; `buried` penalizes reply pile-ons — and since counts refresh from the live node whenever the virtualized timeline re-renders a seen post (scan()'s cached branch), pileup tracks a thread as it GROWS; a post is only ever stale while it stays off-screen. `topOpps()` sorts by the active `dockSort` and slices to 25. Author follower counts are enriched best-effort via `maybeFetchReach`.

**Find spots (off-page, optional).** `findSpots()` sends `TWTTR_GET search-v3` (RapidAPI, governed by a monthly budget + token bucket), picks discovery tweets, scores them with the same `SCORE_POSTS` path, and adds high scorers as `source: "search"` opps.

**Draft (Claude, Sonnet).** `openDraftFromEl()` / a dock click → `draftFor(req)`. It resolves the promote product, paints the loading panel, and sends `DRAFT_REPLY {author, text, context, angle, product, steer}`. `service-worker.ts` reads stored voice + niche and calls `draftReply()` (claude-client.ts) → `claude-sonnet-4-6`, `X_DRAFT_SYSTEM`, `max_tokens 400`, returning plain text (not JSON). The user message now carries a **grounding context block** (`draft-context.ts:buildDraftContext` — niche, the scorer's reason/category, an honest author line from cached reach data): specificity is a ranked variable in the 2026 pipeline (X LLM-grades replies 0-3 on big-author threads + models a slop score, per the open-sourced code), and these strings were already known. The system prompt stays byte-stable for the invariant guard; the enrichment is measured bare-vs-enriched by `scripts/eval-draft-reply-live.mjs` (stage 2 — own-reply exemplars + the measured-angle line — is gated on that eval's delta). The reply is post-processed by `stripDashes()` — a deterministic safety net that strips em/en dashes and hyphenated compounds while shielding URLs/handles/emails. `lastDraft` holds the request so angle chips, steer, and Regenerate re-draft the same post.

**Insert (DOM, never posts).** `doInsert(text)` → `insertReply()` finds the reply DIALOG's composer (explicitly never the page's main "what's happening" box), clicks Reply if needed, and `typeInto()` does a verified one-shot insert (`exec`→`paste`→`beforeInput`, length-aware `complete()` check — typed cadence is avoided because repeated programmatic inserts poison DraftJS). On success it likes the post once (`likePost`, delayed a human beat), then `recordReplyAndNudge()`.

**State / persistence.** `recordSentReply()` → `logSentReply()` appends a `SentRecord` to `replyLog.sent` (capped `SENT_MAX = 500`), bumps `replyLog.daily`/`total`/`times`, adds the post id to `commentedIds` (drives the green `✓ Commented` badge), and persists the whole `replyLog` to `chrome.storage.local` under `X_REPLY_LOG_KEY`. `recordReplyAndNudge()` also updates per-author last-reply times and the normalized-draft dedup list, then returns one nudge via `pickReplyNudge`. Pause state persists under `X_PAUSED_KEY`. The `seen`/`opps`/`liked`/`followed` maps are in-memory per page-session.

## What is honest about it / limits
- **Draft-only is the keystone.** Nothing auto-posts. `insertReply` targets the reply-dialog composer only and the panel footer says "Inserts into X's reply box — you review and post. Never auto-posts." The like fires only on Insert (commitment), once per post, after a human delay.
- **Pace / reputation guards are real and cross-session** (X penalties attach to the account): hourly volume (`replyLog.times` vs `REPLY_HARD_PER_HOUR`), same-author spread (`AUTHOR_REPEAT_TTL` 3 days), and duplicate-reply detection (`isDuplicateReply` over recent normalized drafts). Follows are paced too (`FOLLOW_MIN_GAP_MS` 20s jittered + `FOLLOW_HOUR_CAP` 15/hr) and `followAuthor` can only follow, never unfollow. Goobi's mood deliberately refuses to celebrate a reply once you're past the hourly line.
- **The reply count is a proxy, not a confirmation.** "Replies sent today" counts every Insert / clipboard-fallback / mark-commented click — the click is the signal; the code does NOT verify you actually posted.
- **Score split: model = content/fit ONLY.** The Haiku score judges the post's text + niche fit and is explicitly told to ignore recency, likes, and reply counts. Freshness, reach, reciprocity, and pile-up are all computed locally in `effectiveScore`. `reachFactor`/`reciprocityFactor` are PROXIES — follower count is real (when Twttr-enriched) but reply-back propensity is inferred from following/followers ratio; `freshnessFactor` is a fixed decay curve, not measured visibility.
- **Outcome learning IS wired (best-effort).** `runMeasurePass` (`x-copilot.ts:2177`, fired daily on dock open via `maybeRunDailyLearn`) pulls your recent replies via `user-replies-v2`, matches each back to a stored `SentRecord` (`matchOutcomes`), and writes real likes/replies into `SentRecord.outcome`; those feed `aggregateAccounts` (learn-stats.ts) → the per-account "who you show up with" scores. Caveats: needs a Twttr key, runs once/day, and a Tier-2 measured score only appears after `N_MIN_OUT = 4` settled outcomes — so the DATA is sparse, not absent. NOTE: the *replies* `effectiveScore` ranker does not yet *consume* this signal (only the Targets suggestion ranker does); wiring that consumption is a separate, contested decision (a prior review flagged a coverage mismatch — learned scores are inert for the cold authors the dock surfaces most).
- **Off-page opps degrade gracefully.** A search-discovered post isn't in the DOM, so `findPost` (strict id match — never a same-author lookalike) returns nothing and Insert tells you to open the post first; Draft/Copy still work.
- **DOM-scraped, best-effort.** Engagement counts, avatars, verified badges, and display names come from X's DOM (quote-tweet-aware: always the OUTER post). Anything unreadable is simply omitted, never guessed.
- **Per-session cost cap.** `MAX_SCORE_CALLS = 40` bounds Claude spend/ToS exposure per page; hitting it surfaces a one-time toast pointing at ⟳ Rescan (which resets the cap and clears `seen`).

## Key files
- `src/content/x-copilot.ts` — the whole content-script pipeline: scan/flush, badge/addButton, the dock (renderList/topOpps/effectiveScore/inReachSweetSpot), findSpots, draftFor/lastDraft, doInsert/typeInto/insertReply, recordReplyAndNudge/recordSentReply/logSentReply, likePost/followAuthor.
- `src/lib/prompts.ts` — `X_SCORE_SYSTEM`, `X_DRAFT_SYSTEM`, and `REPLY_ANGLES` (the 6 angle directives + labels used for badge tags and the panel chips).
- `src/lib/claude-client.ts` — `scorePosts` (Haiku, JSON), `draftReply` (Sonnet, plain text), `stripDashes` (dash/hyphen safety net), `callDirect`/`rawCall` (BYO-key direct Anthropic fetch).
- `src/background/service-worker.ts` — `SCORE_POSTS` and `DRAFT_REPLY` message handlers (inject stored niche/voice/products), plus `GET_FAVICONS` and the governed `TWTTR_GET`.
- `src/lib/reply-hygiene.ts` — `isDuplicateReply`, `normalizeReply`, `pickReplyNudge`, `REPLY_HARD_PER_HOUR` (the pace/dedup guards). `src/lib/human-pacing.ts` — `humanDelayMs`, `jitterGap`.

## Before you change it
- **Two Claude models, two cost tiers, on purpose:** scoring is Haiku (cheap, batched, JSON, capped at 40 calls/session), drafting is Sonnet (quality, one call per draft, plain text). Don't collapse them or switch the draft to JSON — `draftReply` returns free-form prose precisely because JSON-wrapping reply text is fragile.
- **Raw model score vs `effectiveScore` are different numbers.** `seen`/`opps` store the raw 0-1 model score; everything shown to the user (badges, dock, sorting, the `THRESHOLD = 0.6` gate is on raw, but the displayed %/verdict is `effectiveScore`) runs through the local multiplicative formula. Editing the prompt changes fit; editing `effectiveScore`/`freshnessFactor`/`reachFactor` changes ranking. Know which you're touching.
- **The draft-only + pacing guarantees are load-bearing trust features.** `insertReply` must keep targeting the reply DIALOG composer (not the main tweet box, which posts to everyone). The like-on-Insert-once, follow caps, hourly/duplicate/spread nudges, and "never auto-post" footer are the product's anti-spam keystone — don't loosen them without intent. See MEMORY: Goobi's auto-like on the replied-to post is intentional, kept by the owner; do not "fix" it.
- **DraftJS is hostile to programmatic input.** `typeInto` deliberately does NOT type word-by-word in production (repeated inserts poison the editor); it's a verified one-shot with length-aware success. Changing the insert strategy risks half-filled reply boxes.
- **X's virtualized timeline + closed shadow roots:** dedup is by status id, badges are idempotent and re-applied from the `seen` cache on remount, `findPost` is strict id-only (never a same-author lookalike), and panel inputs live in closed shadow roots with `trapKeys` so X's single-key shortcuts don't hijack typing. Respect these when adding DOM logic.
- **Tests:** the helper libraries have unit coverage — `scripts/test-hygiene.mjs` (reply dedup/nudges), `scripts/test-pacing.mjs` (human pacing) — but `x-copilot.ts` itself (scan/flush/effectiveScore/typeInto/doInsert) has **no** unit tests; it's verified via `tsc --noEmit` + the build + manual on-page testing. The gate is `tsc + build + scripts/test-*.mjs`. There is no test asserting `effectiveScore`'s curve or that `insertReply` avoids the main composer — change those carefully.
- **`SentRecord.outcome` IS written and read** — `runMeasurePass` writes it (`x-copilot.ts:2198`) and `aggregateAccounts` reads it (`learn-stats.ts:108,121`). It's sparse (needs a Twttr key + ≥4 settled outcomes per account before a measured score shows), but it is NOT dead weight — don't re-stub it. This is the data that makes the audit's "measure-first" tests runnable on data already in hand.
